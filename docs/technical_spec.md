# Техническое задание / постановка на разработку

**Статус:** учебный документ, версия 1.0, не подписан заказчиком. Связанный BRD — `business_requirements.md`.

## Контекст

Разработать локальную витрину энергопотребления одного предприятия на основе CSV с интервальными измерениями; дать возможность анализировать потребление по времени и типу нагрузки и считать условные тарифные затраты.

## Pipeline и компоненты

1. Источник — CSV со схемой UCI Steel Industry Energy Consumption (11 колонок).
2. `src/etl.py`: проверить схему/типы/качество; нормализовать категории; сформировать staging, измерения и факты.
3. SQLite — демо-хранилище, PostgreSQL — вариант целевого DWH.
4. Выгрузить CSV-таблицы для Power BI; собрать витрину `vw_energy_enriched`.
5. Отчёт: автономный HTML (`src/build_report.py`) + Streamlit (`dashboard/app.py`).

## Описание модели

**Гранулярность факта:** одна строка = одно 15-минутное измерение потребления **всего предприятия** в локальном времени источника. Один timestamp уникален в рамках файла. Тип нагрузки — категориальная характеристика интервала, а не отдельный цех.

Факт `fact_energy_readings` имеет `reading_id`, `timestamp_local`, `date_key`, `time_key`, `load_type_key`, `usage_kwh`, вспомогательные показатели качества электроэнергии. Измерения `dim_date` / `dim_time` / `dim_load_type`. Синтетический тариф хранится в `dim_load_type`.

## Бизнес-правила

- При `source=uci` ожидать ровно 35 040 записей; при демо-режиме любой корректный объём.
- Невалидный формат даты, дубликаты времени, отрицательное потребление, пропущенные поля и некорректные категории останавливают загрузку с явной ошибкой.
- Время должно попадать в 15-минутную сетку и соответствовать NSM.
- День недели / WeekStatus должен соответствовать timestamp.
- Все отображаемые суммы фильтруются по месяцу и типу нагрузки.
- Пустая выборка не должна вводить в заблуждение; Streamlit показывает отсутствие данных.
- Отчёт не должен округлять значения до агрегирования; отображение округляется отдельно.
- Стоимость: `SUM(usage_kwh × demo_tariff_krw_kwh)`.
- Запрещено подписывать кВт·ч как кВт и трактовать `co2_source_value` как доказанные тонны CO₂.

## API / интерфейс

Локальный HTML: 3 вкладки, два селектора; основные KPI синхронно пересчитываются с графиками. Streamlit: фильтр диапазона дат и множественный фильтр типов. Дополнительные REST API не входят в scope.

## Критерии приёмки

- AC-01: после `python -m src.etl --source demo` SQLite содержит 8 640 строк факта (на включённом демо-файле).
- AC-02: количество фактов равно количеству raw-строк; разность `SUM(usage_kwh)` меньше 0.0001 кВт·ч.
- AC-03: корректный локальный отчёт `dashboard/report.html` открывается без сервера и содержит 3 страницы.
- AC-04: фильтр месяца и типа нагрузки пересчитывает KPI и графики согласованно.
- AC-05: `.csv` exports образуют 3 измерения + факт + staging.
- AC-06: `pytest` выполняет проверки качества, дублирования и повторной загрузки.

## Задачи для разработчика

- **TASK-01 · ETL:** парсер CSV, типизация, DQ-правила, исключения.
- **TASK-02 · DWH:** создать staging, dim, fact, ключи/индексы, витрину.
- **TASK-03 · BI:** фильтры, 3 страницы, KPI, обзор и визуализация профиля.
- **TASK-04 · QA:** сверка KPI и негативные сценарии.
- **TASK-05 · Docs:** Data Dictionary, описание допущений, handover.

## Не входит в scope

Продакшен-авторизация, расписание ETL, мониторинг SLA, real-time ingestion, фактические тарифы, расчёты по цехам, промышленная Big Data инфраструктура, опубликованный Power BI Service.
